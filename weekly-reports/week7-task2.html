MQTT Cloud Dashboard with Relay Control

Control a bulb through an ESP32 relay using MQTT-based cloud messaging and an Adafruit IO dashboard.

1. Overview

This experiment marks the transition from local subnet HTTP communication to internet-scale IoT infrastructure. Instead of requiring the user device to be on the same local Wi-Fi network, control commands are routed through an online MQTT cloud broker hosted on Adafruit IO.


The ESP32 maintains a persistent, lightweight MQTT connection to the cloud broker and subscribes to a dedicated data feed. When a switch toggle is actuated on the remote Adafruit IO dashboard, the broker dispatches the payload to the ESP32 in real time. The microcontroller decodes the command and actuates digital pin GPIO 23, driving an electro-mechanical relay module that securely switches an AC-powered incandescent bulb.

2. Objective

The primary objective of this assignment is to control a mains-powered bulb from an Adafruit IO cloud dashboard by sending MQTT messages to an ESP32, which switches a 5V relay module. Commands travel through the internet and not through the local Wi-Fi subnet, so the dashboard can be used from any network.


  • Understand MQTT publish / subscribe messaging: broker-centric, asynchronous delivery of payloads through a named feed.
  • Control hardware through cloud messaging: switch a physical load from a browser dashboard without being on the same local network.
  • Interface a relay with ESP32 logic signals: drive a 5V relay input from a 3.3V GPIO pin and switch a 230V AC bulb through its contacts.
  • Evaluate response time: observe the delay between a dashboard click, the cloud broker and the relay actuation.
  • Design an event-driven control flow: keep the connection alive in loop() without blocking the microcontroller.

3. Problem Statement

A local web server, as used in Task 01, only works while the controlling device is on the same Wi-Fi network as the ESP32. It also requires the ESP32 to run its own server and to have an address that the client can reach.


This experiment addresses the following problem: How can a relay-controlled bulb be switched from a dashboard anywhere on the internet, without a public IP address or a web server on the ESP32?


The solution uses a cloud MQTT broker (Adafruit IO) as an intermediary. The ESP32 opens an outgoing connection to the cloud, subscribes to a feed, and acts on the messages that the dashboard publishes to that feed.

4. Introduction

MQTT (Message Queuing Telemetry Transport) is a lightweight publish / subscribe protocol designed for small devices and unreliable networks. Clients do not talk to each other directly. They connect to a broker, which receives messages published to a topic and forwards them to every client that has subscribed to it.


Adafruit IO is a cloud IoT platform that provides an MQTT broker, data feeds and browser dashboards with blocks such as toggle switches and gauges. A feed stores the values of one data stream, and a dashboard block can read from or write to a feed.


ESP32 and Relay: the ESP32 connects to Wi-Fi and, through the Adafruit IO Arduino library, to the broker. A relay module lets the low-power GPIO signal switch a separate high-voltage circuit through isolated contacts, so a 230V bulb can be controlled safely when the wiring is done correctly.

5. Working Principle

The system follows a publish / subscribe cycle. Each dashboard action travels to the ESP32 through the cloud broker and ends as a relay state change:

Step 1 — Dashboard Toggle

The user clicks the toggle block on the Adafruit IO dashboard bulb_control (Figure 14.2). The block writes its ON or OFF value to its feed.

Step 2 — Adafruit IO Broker

The new feed value is received by the Adafruit IO MQTT service, which forwards it to every client subscribed to that feed.

Step 3 — ESP32 Subscription

The ESP32 joins Wi-Fi with connectWiFi(), connects to io.adafruit.com on port 1883 with connectMQTT() and subscribes to the feed bulb-control. In loop(), readSubscription(5000) waits up to 5 seconds for a message.

Step 4 — Command Decoding

processBulbCommand() trims the payload and converts it to lower case. "1", "on", "bulb on" and "bulbon" mean ON; "0", "off", "bulb off", "bulboff" and "of" mean OFF. Any other text is ignored.

Step 5 — Relay and Bulb

The sketch writes the relay pin (GPIO 23) HIGH for ON and LOW for OFF and prints Bulb turned ON or Bulb turned OFF. The relay contacts then close or open the bulb circuit.

Reverse Path

The sketch only subscribes to the feed. It never publishes, so the ESP32 does not report the relay state back to the dashboard in the existing implementation.

10. System Architecture

MQTT (Message Queuing Telemetry Transport) operates on an asynchronous Publish/Subscribe paradigm. In this deployment, the publisher, cloud broker, and subscriber interact as follows:

STAGE 01

User UI

Adafruit IO Dashboard
STAGE 02

Cloud Broker

MQTT Broker (io.adafruit.com)
STAGE 03

Edge Device

ESP32 Subscriber
STAGE 04

Logic Pin

GPIO 23
STAGE 05

Isolator

5V Relay Module
STAGE 06

AC Load

230V Bulb
Flow Chain: Adafruit IO Dashboard → MQTT Broker → ESP32 Subscriber → GPIO → 5V Relay Module → 230V Bulb

Publisher → MQTT Broker → Subscriber: Adafruit IO serves as the cloud MQTT broker hosting the dedicated feed named bulb-control. The dashboard acts as a publisher pushing ON / OFF values (1 / 0) to the feed. The ESP32 acts as a persistent subscriber listening for feed events and translating them into physical pin state transitions.

12. Source Code

The sketch below is ESP32_AdafruitIO_MQTT_Cloud_Control.ino from the Task 02 repository, shown exactly as it exists. The Wi-Fi name and password, Adafruit IO username and key are placeholders in the file, so no secrets are displayed.

ESP32_AdafruitIO_MQTT_Cloud_Control.ino 
1#include <WiFi.h>
2#include "Adafruit_MQTT.h"
3#include "Adafruit_MQTT_Client.h"
4
5#define WIFI_SSID "YOUR_WIFI_NAME"
6#define WIFI_PASS "YOUR_WIFI_PASSWORD"
7#define AIO_USERNAME "YOUR_ADAFRUIT_USERNAME"
8#define AIO_KEY "YOUR_ADAFRUIT_IO_KEY"
9
10#define AIO_SERVER      "io.adafruit.com"
11#define AIO_SERVERPORT  1883
12
13WiFiClient client;
14Adafruit_MQTT_Client mqtt(&client, AIO_SERVER, AIO_SERVERPORT, AIO_USERNAME, AIO_KEY);
15
16Adafruit_MQTT_Subscribe bulbControl = Adafruit_MQTT_Subscribe(&mqtt, AIO_USERNAME "/feeds/bulb-control");
17
18#define RELAY_PIN 23
19#define RELAY_ON HIGH
20#define RELAY_OFF LOW
21
22void connectWiFi() {
23  Serial.print("Connecting to Wi-Fi");
24  WiFi.begin(WIFI_SSID, WIFI_PASS);
25  while (WiFi.status() != WL_CONNECTED) {
26    delay(500);
27    Serial.print(".");
28  }
29  Serial.println();
30  Serial.println("Wi-Fi Connected!");
31}
32
33void connectMQTT() {
34  int8_t ret;
35  if (mqtt.connected()) {
36    return;
37  }
38  Serial.print("Connecting to MQTT... ");
39  uint8_t retries = 3;
40  while ((ret = mqtt.connect()) != 0) {
41    Serial.println(mqtt.connectErrorString(ret));
42    Serial.println("Retrying MQTT connection in 5 seconds...");
43    mqtt.disconnect();
44    delay(5000);
45    retries--;
46    if (retries == 0) {
47      while (1); // wait for watchdog to reset
48    }
49  }
50  Serial.println("MQTT Connected!");
51}
52
53void processBulbCommand(String command) {
54  command.trim();
55  command.toLowerCase();
56  
57  if (command == "1" || command == "on" || command == "bulb on" || command == "bulbon") {
58    digitalWrite(RELAY_PIN, RELAY_ON);
59    Serial.println("Bulb turned ON");
60  } 
61  else if (command == "0" || command == "off" || command == "bulb off" || command == "bulboff" || command == "of") {
62    digitalWrite(RELAY_PIN, RELAY_OFF);
63    Serial.println("Bulb turned OFF");
64  }
65}
66
67void setup() {
68  Serial.begin(115200);
69  delay(10);
70  
71  pinMode(RELAY_PIN, OUTPUT);
72  digitalWrite(RELAY_PIN, RELAY_OFF);
73
74  connectWiFi();
75  
76  mqtt.subscribe(&bulbControl);
77}
78
79void loop() {
80  if (WiFi.status() != WL_CONNECTED) {
81    connectWiFi();
82  }
83  
84  connectMQTT();
85  
86  Adafruit_MQTT_Subscribe *subscription;
87  while ((subscription = mqtt.readSubscription(5000))) {
88    if (subscription == &bulbControl) {
89      String command = (char *)bulbControl.lastread;
90      Serial.print("Received command: ");
91      Serial.println(command);
92      processBulbCommand(command);
93    }
94  }
95}

13. Code Breakdown

Libraries and Settings

WiFi.h with Adafruit_MQTT.h and Adafruit_MQTT_Client.h. The broker is io.adafruit.com on port 1883, with the username and key as placeholders.

Feed Subscription

bulbControl subscribes to AIO_USERNAME "/feeds/bulb-control". mqtt.subscribe(&bulbControl) is called once in setup().

GPIO 23 Relay Control

RELAY_PIN 23, RELAY_ON HIGH, RELAY_OFF LOW. The pin is an OUTPUT and starts OFF in setup().

connectWiFi() and connectMQTT()

Join Wi-Fi with a 500 ms retry loop, then connect to the broker. After three failed MQTT attempts (5 s apart) the code waits in while (1) for the watchdog to reset the board.

processBulbCommand()

Trims and lower-cases the text. "1", "on", "bulb on", "bulbon" switch the relay ON; "0", "off", "bulb off", "bulboff", "of" switch it OFF.

loop()

Reconnects Wi-Fi and MQTT if needed, then readSubscription(5000) waits up to 5 seconds for a message, prints Received command: and calls processBulbCommand().

15. Execution Procedure

Steps required to upload the firmware and operate the relay from the dashboard (derived from the sketch and the dashboard setup):

  • 1. Install Arduino IDE, ESP32 board support and the Adafruit MQTT library: the sketch includes Adafruit_MQTT.h and Adafruit_MQTT_Client.h, so the library must be available.
  • 2. Open the sketch: open ESP32_AdafruitIO_MQTT_Cloud_Control.ino in Arduino IDE and select the ESP32 board and COM port.

17. Testing and Verification

End-to-end operational verification across cloud dashboard triggers, serial telemetry logs, and mechanical relay switching:

Turn ON Command

Dashboard ON → MQTT → ESP32 → Relay → Bulb ON

Toggle clicked on Adafruit IO. The sketch treats 1 / on as ON, prints Bulb turned ON and drives GPIO 23 HIGH, closing the relay. The demonstration video shows the bulb lighting up.

Turn OFF Command

Dashboard OFF → MQTT → ESP32 → Relay → Bulb OFF

Toggle turned off. The sketch treats 0 / off as OFF, prints Bulb turned OFF and drives GPIO 23 LOW, opening the relay. The video shows the bulb going off again.

Latency Observation: The system was evaluated targeting sub-second control response between remote browser clicks and physical relay actuation. Observed latency was consistently responsive across standard broadband Wi-Fi, reflecting MQTT's lightweight header overhead, though real-world response naturally varies with network conditions.

18. Problems and Solutions

Problems recorded in the project README, followed by items visible in the evidence (no causes or fixes are invented):

Observed: Feed Creation Returned 400

The Feeds page in Figure 14.6 shows the message "POST …/feeds returned 400". The cause and the fix were not recorded. To add

Problem: MQTT Disconnections

The repository README states that the ESP32 occasionally dropped the MQTT connection because of network latency.

Solution: reconnect logic: loop() calls connectMQTT(), which retries the connection up to three times (implemented in the sketch).

Problem: Relay Logic Level

The README states that some relay modules are active-low, so the HIGH / LOW logic had to match the relay hardware.

Solution: the logic is defined once in RELAY_ON and RELAY_OFF (HIGH = ON in the sketch).

Open Item: Feed Name

The sketch subscribes to bulb-control, while the Feeds page in Figure 14.6 lists a feed with key bulb and the dashboard key is bulb-control. Confirm which feed the toggle block writes to.

Open Item: Account Name in Lab Photos

The dashboard visible on the laptop in the lab photographs shows a different account name (Hisenbergg_007 / Dashboards / Bulb) from the screenshots in Section 14 (harish3105). Confirm which account the code's IO_USERNAME refers to.

22. Safety Notes

⚡

Galvanic Electrical Isolation

The relay module provides physical and optical isolation between the low-voltage ESP32 control circuitry (3.3V/5V DC) and the dangerous 230V AC mains circuit.

🔬

5V Bench Signal Verification

Before connecting high-voltage mains power, the switching logic was pre-tested using low-voltage DC signals and a continuity meter to verify coil actuation and contact integrity.

🦺

Enclosure & Terminal Insulation

All AC wiring connections must use insulated screw terminals and protected enclosures. Never leave live conductors exposed during operation or testing.

⚠️

No Direct Mains Experimentation

Direct mains voltage can cause lethal electric shocks and fires. High-voltage setups must only be tested under controlled laboratory supervision with verified isolation.

23. Key Learnings

🌐

MQTT vs. HTTP in IoT

Recognized why MQTT is preferred for IoT: persistent lightweight TCP connections eliminate HTTP header polling overhead, enabling instant push notifications from the cloud.

🔔

Subscription-Driven Control

Learned how the loop waits for subscription messages (readSubscription) and acts on each payload as it arrives, decoupling the sender from the device.

🔌

Relay Transistor Driver Dynamics

Understood how relay driver boards use flyback diodes and optoisolators to prevent inductive voltage spikes from damaging microcontroller GPIO pins.

Cloud Dashboard Feeds

Gained experience configuring cloud telemetry feeds, dashboard toggle blocks, and secure device authentication on Adafruit IO.
